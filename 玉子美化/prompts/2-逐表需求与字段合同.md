# 2 - 逐表需求与字段合同

> 本文逐表规则适用于整页美化。弹窗任务先走文末“弹窗制作分支”，并读取弹窗专用流程；正文组合弹窗按一个弹窗处理，不受单张来源表限制。

本阶段只处理 `workflow-state.json#currentTable` 指向的当前表。先把用户对这一张表的目标和字段合同说清楚；没有用户确认，不进入设计和实现。

先用大白话介绍当前表是做什么的、现在有哪些信息、哪些地方值得改善。AI 要主动提出具体美化建议并说明理由，但页面目标、保留字段、交互取舍和是否改表都由用户决定。字段合同首次出现时解释为“这个页面会读取哪些列，以及每一列怎么显示”。

## 集中访谈规则

需求讨论采用分组访谈，在一轮中集中解决多个相关决定：

1. 沿着同一主题或互相依赖的决定，一次列出多个清楚、编号的问题并等待用户统一回答；每个问题都要给出 AI 的推荐答案、推荐理由和其他选择的实际影响。无关问题留到下一轮，不把整张表的所有问题一次倾倒给用户。
2. 能从表格、项目状态、现有源码、用户草图或文档中查明的事实由 AI 自己读取，不得要求用户重复说明。只把视觉偏好、交互取舍和制作范围等真正的决定交给用户。
3. 用户回答后先复述新确认的结论，把双方本轮原话追加到访谈记录，再进入下一组尚未解决的决定；已经确认的内容不重复询问。
4. 用户给出初步想法、参考图或回答单个问题，只代表继续讨论，不代表允许编辑页面源码。
5. 在需求与字段合同形成共同理解前不得开始实现，也不得用“先做个版本看看”越过讨论。

## 访谈记录

当前表的访谈记录固定写入项目内 `notes/interview-<sheetKey>.md`。进入本阶段时先读取已有记录；文件不存在时创建。记录只包含本表访谈中的纯对话，按发生顺序反复使用 `## 用户` 和 `## AI` 标明说话人，正文保存对应消息原话。

不得在文件中增加需求摘要、决定清单、AI 推断、待办事项、未决问题、授权状态、流程优化讨论、命令输出或实现日志。某条消息同时包含访谈与其他事务时，只摘录与当前表访谈直接相关的原话，不改写内容。任务恢复、上下文压缩或交接后，以真实表格、项目状态和完整访谈对话共同恢复上下文；实现阶段也直接阅读对话，不另造一份整理版需求。

## 获取真实上下文

1. 运行 `npm run project:status -- --project <project.json> --json`，确认当前表不是已终结状态。
2. 从 `tables/generated/tables.json` 读取当前表的 `sheetKey`、表名、表头和有代表性的真实数据形状；不得用五页参考源码或外部文档替代真实表。
3. 如项目已有该表的 notes、字段合同或失效 item，先说明可继承内容与已经失效的部分。
4. 只有用户明确提出要使用酒馆、SillyTavern、TavernHelper 或酒馆输入框等外部能力时，才读取 `docs/architecture-notes.md` 和 `docs/sillytavern-api.txt`；没有这类明确需求时不要主动读取。用户明确要求宿主 DOM 时，可以按用户指定的选择器和行为实现，并在设计中记录找不到目标元素时的降级处理；普通表格仍不主动访问宿主 DOM。

## 逐表需求

围绕当前表与用户逐项确认：

- 页面要解决什么阅读或操作问题；
- 信息层级、默认排序/筛选、空态、异常态和长内容处理；
- 视觉方向、密度、移动端宽度和必要的本地交互；
- 四个 Runtime 导航 action 中实际需要哪些。必须完整列出并让用户逐项选择，不得由 AI 预先删减：
  - `back()`：返回上一层页面；
  - `previousTable()`：切换到上一张表；
  - `nextTable()`：切换到下一张表；
  - `editCurrentTable()`：打开当前表的通用编辑页。

首次说明时先使用上述大白话名称，再补充代码名。AI 要为四项分别给出建议，但不能把未提及视为拒绝，也不能只展示 AI 认为适合的子集。相关问答作为原话保留在访谈对话中。

不要把数据库写入、任意跨表读取、通用 AI、世界书或内部路由包装成页面需求。受控生图与声明式展示按本地 `docs/runtime/host-capabilities.md` 使用，不访问宿主内部对象。

## 字段合同

为每个实际使用字段记录：

| 内容 | 要求 |
| --- | --- |
| 真实字段名 | 与当前 generated 表头经 Unicode NFKC 后精确匹配 |
| 页面用途 | 标题、正文、时间、状态、媒体地址等明确语义 |
| 解析规则 | 原始类型、分隔符、容错、空值和默认显示 |
| 展示位置 | 对应的信息区块或交互控件 |
| 安全处理 | 默认使用 `textContent`；URL、富文本或资源需说明边界 |

真实表允许有未使用字段；item 只声明实际依赖字段。不得声明不存在的字段，也不得以猜测字段名代替向用户解释冲突。

## 跳过与改表分支

先区分两个大白话概念：删除表表示最终表格产物里不再有它；跳过表示表仍保留，只是不制作它的美化页面。用户明确删表时删除对应 Markdown、重建并 refresh，让它直接退出队列，不要再调用 `project:skip-table`。

若用户明确决定整张表不制作，复述表名和原因后执行：

```powershell
npm run project:skip-table -- --project <project.json> --table <sheet-key> --reason <user-reason>
```

原因必须非空。AI 不得代替用户作出跳过决定。恢复制作使用 `--resume`，恢复后仍从本阶段重新确认。

若需求无法由现有字段表达，不要立即改 JSON。先说明对字段合同、已有 item、generated JSON、结构哈希和数据兼容性的影响；取得用户确认后，只编辑 `tables/source/*.md`，再执行：

```powershell
npm run tables:cli -- build <source-dir> <generated.json>
npm run project:status -- --project <project.json> --refresh
```

刷新可能使当前表或其他受影响 item 进入 `invalidated`；必须从对应表重新逐表确认。`tables/original/imported.json` 不得改写。

## 完成条件

向用户展示“当前表需求摘要 + 字段合同 + 明确不做的能力”，用大白话说明建议的下一步设计方向和影响，获得用户确认，并把记录保存到当前项目 notes。这里的确认只允许进入设计讨论，不等于允许写源码。之后进入 `3-逐表设计与实现.md`。当前表尚未确认时不讨论下一张表。

## 宿主能力交接与生图讨论

普通制作不要求小手机源码。涉及字体、主题、生图等能力时，先读取 `docs/runtime/authoring-workflow.md`、`docs/runtime/host-capabilities.md` 和类型/示例，核对接口与模拟覆盖，再讨论效果。缺资料属于工具维护问题，不要求普通用户提供源码、不猜接口。

生图访谈必须先说明画框显示宽高、比例和窄屏变化，区分显示尺寸与出图分辨率；展示“表格字段＋构图要求”的完整拼接提示词，并集中询问用户要不要补充自己的提示词内容。只有确认后的构图与补充才能写入 `promptSuffix`。

制作期模拟永远只使用测试图片和内存数据，不调用真实生图、不读取密钥、不消耗额度，不提供切换真实生图的入口。用户明确要求最后统一模拟时，每表先记 `not-run`，不重复追问、不虚报通过；不省略逐表需求与结果确认。

## 弹窗制作分支（先选接口）

涉及弹窗时先读取 `docs/runtime/popup-authoring-workflow.md`。明确告诉用户“小手机有三个弹窗接口”：**弹幕**、**弹窗／浮窗**、**弹窗／插入正文**，先问做哪一个；不用“这份展示”代替“弹窗”。弹幕和弹窗／浮窗只能单表；只有弹窗／插入正文可以多表组合，选定它以后才问单表还是组合。已明确的选择不重复询问。内容、排版、交互在接口及来源确定之后再讨论。

弹窗访谈只确认接口、来源表、使用字段、内容排版、分页和用户可见交互。当前显示哪一行、是否最新、哪条记录触发以及宿主如何筛选数据，属于小手机运行时提供当前快照/事件的职责，不属于玉子美化决定。除非用户明确要求历史记录列表或行选择器，否则不得提出这些问题。

整页美化仍逐表；弹窗一次制作一个，正文组合弹窗的多个来源表共同组成一个制作单元，不拆散、不批量越过确认。使用 `project:add-display` 登记，不覆盖来源表的已有页面；模拟延后与真实状态记录规则不变。

图片能力必须单独确认：制作弹窗／插入正文时，必须主动问“要不要加生图按钮？”，并说明可以只共用页面图片而不加按钮；不得把某个用户选择不加变成通用默认。弹幕和弹窗／浮窗不支持点击生图，应说明限制，不提供不可用选项。图片标识也必须问：用户选择稳定标识字段，AI 检查真实值的空值、重复与稳定性；即使只有一行也不能省略，不擅自选 row_id、姓名、提示词或行位置。已明确的决定不重复问。标识确认是图片归属，不是弹窗显示记录筛选。
