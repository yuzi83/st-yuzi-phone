# 4 - 单表检查与模拟

> 本文逐表规则适用于整页美化。弹窗任务先走文末“弹窗制作分支”，并读取弹窗专用流程；正文组合弹窗按一个弹窗处理，不受单张来源表限制。

本阶段承接已经一次制作完成的当前表，只询问是否打开制作期模拟，并在记录结果后确认该表结论。模拟可以跳过，但询问和结果记录不能跳过。

询问模拟时先用大白话解释：制作期模拟是在本机临时看看页面效果和数据变化，不会修改真实酒馆数据库，也不等于已经在真实 SillyTavern 中验证。结合当前表风险给出是否建议模拟及理由，但由用户决定运行或跳过。

## 内部制作结果

询问预览前只确认制作阶段已经完成以下内部动作，不重复运行或逐项向用户展示：

- 当前表只有一个 item，表名和声明字段与 generated JSON 匹配；
- 源码、entry、编码和项目内路径合同通过；
- CSS 有独立根作用域，JavaScript 无父目录 import、宿主私有标识或数据库全局对象；
- `npm run project:check -- --project <project.json>` 已通过。

失败就返回当前表实现，不得进入模拟或下一表。

## 每表模拟选择

明确询问用户：“是否现在对当前表 `<表名>` 运行制作期模拟？”用户可以跳过；不要替用户默认通过，也不要把静态检查视为模拟结果。

用户同意时运行：

```powershell
npm run preview -- <project.json> --table <sheet-key>
```

预览内容成功出现后，AI 不停下来等待用户操作，继续自动完成以下检查：

1. 在当前表的内存 Mock 数据中新增至少一行有代表性的完整内容，填写当前页面实际使用的字段；该行只用于本轮预览，不写入任何正式表格产物。
2. 确认页面通过订阅实时出现新增内容，并验证主要阅读/弹窗/展开等交互能正确读取该行。
3. 执行一次 Runtime 清理或卸载，再重新构建或挂载当前页面；需要时切换表格后再切回，确认旧实例已清理、Mock 内容仍可用、没有重复事件监听。
4. 检查生命周期日志和浏览器控制台，确认没有异常、重复触发或残留实例；同时覆盖当前页需要的常用手机宽度和实际使用 action。

以上步骤连续自动执行，不再逐项询问用户。根据真实观察记录 `passed` 或 `failed`；只有全部通过才能向用户说明预览无误。失败必须说明场景和日志，留在当前表修复后重新模拟。

用户拒绝本次模拟时记录 `skipped` 和原因；尚未获得选择时保持 `not-run`。使用与原 item 相同的路径、字段和资源，加 `--replace` 更新准确的 `preview-status` 与说明，例如：

```powershell
npm run project:add-item -- --project <project.json> --table <sheet-key> --id <item-id> --mount <mount.js> --field <field-name> --replace --preview-status passed --preview-notes <说明>
```

不要把 `not-run`、`skipped` 或 `failed` 改写成通过。

## 当前表结果确认

向用户展示当前表实际完成的页面效果、制作期模拟状态和已知限制；例行的 item 登记、路径核对和静态检查不单独展开，除非其中曾失败或会影响用户决定。随后给出下一步建议和原因，请用户确认当前表结果。只有用户确认后，当前表才能保持 `completed` 并推进队列；若用户要求修改，留在当前表回到相应步骤。

确认后重新读取 `project:status --json`：

- 还有 pending/invalidated 表：只进入下一张当前表的 `2-逐表需求与字段合同.md`；
- 全部表为 `completed` 或 `skipped`：进入 `5-汇总确认与交付.md`。

本地结果始终称为“制作期模拟”，不得声称已验证真实 SillyTavern 的 CSP、路由、数据库、IndexedDB、主题叠加、滚动恢复、Blob 资源或生命周期。

## 生图与延后模拟

制作期模拟永远只使用本地测试图片，不调用真实生图、不读取密钥、不消耗额度。详见 `docs/runtime/authoring-workflow.md`。用生图测试场景分别检查成功替换、失败保留、关闭/不可用、防重复、数据更新和清理重挂载。用户已明确最后统一模拟时，各表先记 not-run，不反复询问，也不能标成 passed 或 skipped。

## 弹窗制作分支（先选接口）

涉及弹窗时先读取 `docs/runtime/popup-authoring-workflow.md`。明确告诉用户“小手机有三个弹窗接口”：**弹幕**、**弹窗／浮窗**、**弹窗／插入正文**，先问做哪一个；不用“这份展示”代替“弹窗”。弹幕和弹窗／浮窗只能单表；只有弹窗／插入正文可以多表组合，选定它以后才问单表还是组合。已明确的选择不重复询问。内容、排版、交互在接口及来源确定之后再讨论。

弹窗访谈只确认接口、来源表、使用字段、内容排版、分页和用户可见交互。当前显示哪一行、是否最新、哪条记录触发以及宿主如何筛选数据，属于小手机运行时提供当前快照/事件的职责，不属于玉子美化决定。除非用户明确要求历史记录列表或行选择器，否则不得提出这些问题。

整页美化仍逐表；弹窗一次制作一个，正文组合弹窗的多个来源表共同组成一个制作单元，不拆散、不批量越过确认。使用 `project:add-display` 登记，不覆盖来源表的已有页面；模拟延后与真实状态记录规则不变。

图片能力必须单独确认：制作弹窗／插入正文时，必须主动问“要不要加生图按钮？”，并说明可以只共用页面图片而不加按钮；不得把某个用户选择不加变成通用默认。弹幕和弹窗／浮窗不支持点击生图，应说明限制，不提供不可用选项。图片标识也必须问：用户选择稳定标识字段，AI 检查真实值的空值、重复与稳定性；即使只有一行也不能省略，不擅自选 row_id、姓名、提示词或行位置。已明确的决定不重复问。标识确认是图片归属，不是弹窗显示记录筛选。
