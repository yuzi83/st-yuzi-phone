# 弹窗制作流程

## 先问选择哪个弹窗接口

用户提出弹窗、弹幕、浮窗、插入正文或组合弹窗时，先说明：**小手机有三个弹窗接口：弹幕、弹窗／浮窗、弹窗／插入正文。你想做哪一种？**

必须使用以下用户可见名称，不用“这份展示”“展示形式”代替“弹窗”，不要求用户理解内部代码名。

| 弹窗接口 | 大白话说明 | 可以使用的表格 |
| --- | --- | --- |
| **弹幕** | 内容以弹幕形式出现。 | 只能单表。 |
| **弹窗／浮窗** | 内容出现在浮动窗口中，不插入正文。 | 只能单表。 |
| **弹窗／插入正文** | 内容插入聊天正文里，跟着正文阅读。 | 可以单表，也可以多个表格组合。 |

这是第一轮的选择问题。先说明限制，再等待用户选择；不要在同一轮提前追问单表或组合、具体来源表、内容长短、布局和交互。可以根据用户已表达的目的给推荐与理由，但不得替用户选。

用户已经明确选了其中一种时，复述已有选择后继续，不再重复询问。仅说“组合弹窗”但没有指定接口时，先说明只有弹窗／插入正文支持组合，再确认接口，不默认改成浮窗。

## 按已选接口继续

- 选择**弹幕**或**弹窗／浮窗**：明确只使用一张表，直接列出当前项目真实表名，询问做哪张表；不得提出多表组合建议。
- 选择**弹窗／插入正文**：下一轮问“你想做单个表格的弹窗，还是多个表格组合一起的弹窗？”；可以同时列出真实表名供用户选择来源。已说多表组合就只问来源表，不重复问组合意愿。
- 来源确定后，再集中讨论具体字段、内容顺序、排版、展开/切换等允许的交互。不能用“快速看一眼还是详细阅读”替代弹窗接口选择。
- AI 自行读取真实字段和接口资料，发现不支持的交互先解释；不根据技术枚举声称所有弹窗都支持生图或按钮。

顺序固定：**选择弹窗接口 → 按接口确定单表或组合及来源表 → 内容、排版、交互 → 汇总并询问补充 → 明确开工 → 制作 → 模拟选择 → 结果确认**。

## 当前数据由小手机运行时提供

弹窗访谈只确认接口、来源表、使用字段、内容排版、分页和用户可见交互。当前显示哪一行、是否最新、哪条记录触发以及宿主如何筛选数据，不是玉子美化要决定的内容。

弹窗／插入正文挂载时，小手机运行时会把当前组合快照交给页面。作者通过 `getState()` 读取，并通过 `subscribe()` 接收更新；组合状态包含 `tables`（每张来源表的表头和当前行）、`events`（宿主提供的相关事件快照）和 `settings`（宿主提供的展示设置）。这只是页面读取当前数据的入口，不是让用户选择行的筛选器。

因此，除非用户明确要求“历史记录列表”或“行选择器”，不得询问用户显示哪条、是不是最新一条、哪条记录触发，或让用户决定宿主怎样筛选数据。需要历史列表或行选择器时，才把它作为额外的可见功能单独讨论。

## 组合弹窗是一份作品

整页表格美化仍逐表制作；弹窗制作每次只处理一个已确认的弹窗。只有弹窗／插入正文可以把多个来源表作为一个制作单元，不能用“一次只处理当前表”把同一组合拆散，也不能把组合授权扩大成批量制作多个弹窗或重做来源表页面。

组合逐一确认来源表和必需字段，一个弹窗登记一次，保留已有页面和其他弹窗。不改表结构，不替用户跳过来源表，不把存在于数据里的所有表自动加入组合。弹窗问答原话按一个弹窗写入 `notes/interview-display-<display-id>.md`；AI 从名称派生ID，不要求小白决定。只追加对话，不建 .scratch、不写规格或任务单。

四个整页导航动作不强制套用于弹窗；只讨论所选弹窗接口实际允许的交互。模拟永远只用测试数据和测试图片；已选择最后统一模拟则记 not-run，不重复询问、不写 passed。组合需要核对每张来源表及整体数据变化，模拟工具未覆盖的部分必须如实报告，不能用单表模拟冒充组合通过。

## 制作端登记（AI 操作，不向用户询问代码名）

对应内部 kind：弹幕=barrage，弹窗／浮窗=popup，弹窗／插入正文=inline。通过 `project:add-display` 登记；命令未给kind时必须询问，不默认inline。只有inline允许多个target。

```text
npm run project:add-display -- --project <project.json> --id <display-id> --name <弹窗名称> --kind inline --target <表一字段JSON> --target <表二字段JSON> --mount <mount.js> --preview-status not-run
```

本次限制用于制作入口：barrage/popup多表登记（含replace、dry-run）必须拒绝，拒绝时不能改项目或制作记录。现有文件不自动删改或迁移；底层历史文件读取不在本次流程优化中变更，不将历史兼容行为当作新建指导。

图片能力必须单独确认：制作弹窗／插入正文时，必须主动问“要不要加生图按钮？”，并说明可以只共用页面图片而不加按钮；不得把某个用户选择不加变成通用默认。弹幕和弹窗／浮窗不支持点击生图，应说明限制，不提供不可用选项。图片标识也必须问：用户选择稳定标识字段，AI 检查真实值的空值、重复与稳定性；即使只有一行也不能省略，不擅自选 row_id、姓名、提示词或行位置。已明确的决定不重复问。标识确认是图片归属，不是弹窗显示记录筛选。

正文弹窗滚动由 AI 默认正确处理，不增加用户调查：弹窗／插入正文是酒馆正文的一部分，默认允许滚动传递给外层；确需内部滚动时，到达边缘或内容不足以滚动时仍应允许外层正文滚动。不得照搬手机整页的滚动隔离，默认不要设置 overscroll-behavior: contain/none 或拦截 wheel/touchmove；优先原生 CSS，不加滚轮转发补丁或兼容开关。只有用户明确要求锁定内部滚动时才讨论例外。本规则是制作提醒，不新增专门的模拟检查步骤或开工确认问题；已有模拟选择与如实记录规则不变。
